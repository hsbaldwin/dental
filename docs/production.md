# 실 사용화 프로덕션 프로세스

W치과 웹 서비스(홈페이지 · 예약 · 관리 화면)를 실제 병원에서 운영하기 위한 절차입니다. 외주 · 개발자가 서버를 운영하고, 병원은 관리 화면에서 내용과 예약을 다룹니다.

- 운영 구성: **국내 클라우드 서버 1대** · Docker · Caddy(HTTPS) · SQLite 파일 하나(서버 1대 구조, 여러 대로 늘리지 않음)
- 자동화: `deploy/`(배포 · 되돌리기 · 운영 도우미 · 예약 작업), `scripts/`(점검 · 백업 · 복구), `.github/workflows/`(CI · 이미지)
- 이 문서의 숫자(보관 180일 등)는 관리 화면 → 예약 규칙의 '개인정보 보관 기간'을 바꾸면 함께 바뀝니다.

---

## 1. 한눈에

```
   [개발자 PC]                 [GitHub]                          [클라우드 서버 1대 · 서울 리전]
  로컬 npm run local  ──push──▶ CI: 테스트 · 이미지 · 배포 연습 ─┐
                               │                               │   Caddy (HTTPS, 80/443)
                       v1.2.0 태그 ─▶ 이미지(GHCR) ─────────────┼──▶ ├─ 운영      127.0.0.1:3000  w-dental
                                                               │   └─ 스테이징 127.0.0.1:3100  w-dental-staging
   STAGE=staging deploy.sh v1.2.0 → 확인 → deploy.sh v1.2.0 ───┘        │
                                                                       ├─ 매시 · 매일 암호화 백업 → 국내 오브젝트 스토리지
                                                                       └─ 상태 감시(/api/health) · 직원 웹훅 알림
```

| 역할 | 하는 일 |
|---|---|
| 개발자(운영 담당) | 서버 · 배포 · 백업 · 감시 · 장애 대응 · 보안 업데이트 · 매월 접속기록 점검 준비 |
| 병원 담당자(실장 등) | 관리 화면 내용(병원 정보 · 진료비 · 의료진 · 휴진 · 공지) · 스테이징 확인(문구 · 금액) · 예약 처리 |
| 개인정보 보호책임자(대표원장) | 처리방침 승인 · 월 접속기록 점검 확인 · 유출 시 통지 · 신고 결정 |

## 2. 환경

| 환경 | 주소 | 데이터 | 용도 |
|---|---|---|---|
| 로컬 | `npm run local` (http://localhost:3000) | `data/local.db` 예시 데이터 · 시간 이동 | 개발 · 화면 확인 |
| 체험판 | `npm run build:demo` → `dist/demo` | 브라우저 안 가짜 데이터 | 병원 · 외부 공유용 시안 |
| 스테이징 | `staging.<도메인>` (비밀번호 · 검색 제외) | 가짜 데이터, 문자 발송 안 함 | 운영과 **같은 이미지**로 배포 전 확인 |
| 운영 | `<도메인>` | 실제 데이터 | 환자 · 직원 |

- 스테이징과 운영은 같은 서버의 다른 compose 프로젝트입니다(비용 1대). 설정 파일은 `deploy/staging.env` · `deploy/production.env` — 저장소에 올리지 않습니다(`.gitignore`).
- 로컬 예시 데이터로 만든 DB는 표시가 남아 운영 점검에서 막힙니다. 운영은 새 DB로 시작합니다.

## 3. 변경 흐름 (릴리스)

1. **요청**: 병원 → 개발자(문구 · 기능 · 오류). 받은 날짜와 요청자를 이슈에 적습니다.
2. **브랜치 → PR**: CI가 자동으로 테스트(디자인 · 문구 규칙 포함), 이미지 빌드, 실제 배포 스크립트로 배포 · 깨진 배포 자동 되돌림 · 복구 연습 · Caddy 설정 검사를 합니다. **CI가 초록이어야 합칩니다.**
3. **스테이징 배포**: `STAGE=staging deploy/deploy.sh v1.2.0-rc1` (태그를 먼저 올려 이미지가 생긴 뒤)
4. **스테이징 확인표**(아래 부록 B): 휴대폰 390px · 크게 보기 · 소리 · 예약 1건 끝까지 · 관리 화면에서 확정 → 문자 기록.
5. **병원 확인**: 환자에게 보이는 문구 · 금액 · 의료진 정보가 바뀌면 병원 담당자가 스테이징에서 확인하고 승인(메시지로 남김).
6. **태그**: `git tag v1.2.0 && git push origin v1.2.0` → 이미지 `ghcr.io/hsbaldwin/dental:v1.2.0`.
7. **운영 배포**: `deploy/deploy.sh v1.2.0` — 점검(`--strict`) → 배포 전 백업 → 교체 → 상태 확인 → 실패하면 자동 되돌림 → 직원 웹훅에 결과.
8. **기록**: `CHANGELOG.md`에 버전 · 날짜 · 바뀐 점(환자 화면 / 직원 화면 / 운영) · 병원 확인 여부.

**배포 시간**: 진료 시간 밖(평일 오후 7:30 이후 또는 일요일)에, 다음 날 진료 전에 다시 확인할 수 있을 때만. 금요일 밤 · 연휴 전날은 피합니다.

**긴급 수정**(예약이 안 되는 오류 등): 스테이징 확인을 예약 1건으로 줄이고 바로 배포, 다음 날 확인표 전체를 하고 `CHANGELOG.md`에 '긴급'으로 남깁니다.

**스키마 규칙**: 마이그레이션은 추가만(열 · 표 · 색인, `server/db.js`의 `MIGRATIONS`). 지우거나 이름을 바꿀 때는 두 번에 나눠 배포합니다. 그래야 되돌려도 이전 버전이 같은 DB로 돕니다.

## 6. 장애 대응

| 등급 | 예 | 목표 | 첫 조치 |
|---|---|---|---|
| 1 | 사이트가 안 열림, 예약이 안 됨, 잘못된 시간에 예약이 잡힘 | 30분 안 복구 | **되돌리기 먼저**(`deploy/rollback.sh`), 병원은 전화 예약으로 안내 |
| 2 | 문자가 안 나감, 실시간 표시 멈춤 | 당일 | 문자 업체 · 웹훅 확인, 병원은 확정 연락을 전화로 |
| 3 | 표시 오류, 문구 오타 | 다음 배포 | 이슈로 기록 |

- **알림 경로**: 외부 상태 감시(`https://<도메인>/api/health`, 1분 간격, `X-Health-Token` 헤더) → 개발자 휴대폰 / 앱 안의 운영 알림(문자 실패 · 백업 지연) · 배포 결과 → 직원 웹훅.
- **연락망**: 개발자(1차) → 개발자 대체 연락처 → 병원 담당자 → 대표원장. 오픈 전에 이름 · 번호를 이 문서 사본(저장소 밖)에 적어 병원과 나눕니다.
- **순서**: 확인(`ops.sh status`, `ops.sh logs`) → 되돌리기 또는 우회 → 원인 → 고침 배포 → 기록(부록 C).
- **데이터가 망가졌을 때만 복구**: `deploy/ops.sh restore <배포 전 백업 파일>` — 복구 시점 이후 예약은 사라지므로, 관리 화면 기록과 문자 발송 기록으로 그 사이 예약을 확인해 직원이 다시 넣습니다.

### 개인정보 유출 의심

1. **즉시 차단**: 관리 화면 IP 제한(`deploy/edge.env`의 `ADMIN_ALLOW_IPS`), 의심 계정 삭제, 모든 직원 비밀번호 변경, 필요하면 앱 중지.
2. **사실 확인**: 접속기록(누가 · 언제 · 어디서 · 무엇을), 서버 기록, 내려받기 기록. 증거는 지우지 않고 보관.
3. **72시간 안 통지**: 유출을 안 때부터 72시간 안에 해당 정보주체에게 유출 항목 · 시점 · 경위 · 피해 줄이는 방법 · 병원 대응 · 문의처를 알립니다.
4. **신고**: 1천 명 이상이거나, **민감정보(건강 정보)가 포함되거나**, 해킹 등 외부 불법 접근이면 72시간 안에 개인정보보호위원회 또는 한국인터넷진흥원(KISA)에 신고합니다. 판단은 보호책임자가 하고 개발자가 자료를 준비합니다.
5. **재발 방지**: 원인 · 조치 · 바꾼 설정을 기록하고 다음 월 점검 때 확인합니다.

## 7. 백업 · 복구

| 항목 | 정한 것 |
|---|---|
| 언제 | 진료 시간 매시 + 매일 03:10 + 배포 직전(`pre-deploy-<버전>`) |
| 어떻게 | 운영 중 안전한 사본(`VACUUM INTO`) → 사본 무결성 검사 → **AES-256-GCM 암호화**(`BACKUP_KEY`) |
| 어디에 | 서버 볼륨(`/data/backups`) + 국내 리전 오브젝트 스토리지(rclone) |
| 얼마나 | 48시간 안 모두 · 14일 하루 1개 · 8주 한 주 1개 · 배포 전 사본 최근 10개. **어떤 사본도 개인정보 보관 기간(180일)을 넘기지 않음** — 파기한 개인정보가 백업에 남지 않게 |
| 목표 | 잃을 수 있는 예약 최대 1시간 치(RPO 1시간), 복구 1시간 안(RTO 1시간) |
| 키 | 서버의 `production.env`와 **서버 밖 비밀번호 관리자**에 함께. 키를 잃으면 백업을 풀 수 없음 |
| 확인 | 매주 자동 `verify`, 분기마다 스테이징에 실제 복구 |

명령: `deploy/ops.sh backup` · `deploy/ops.sh verify` · `deploy/ops.sh restore <파일명>` (복구 전 현재 DB는 `before-restore` 이름으로 남음).

## 8. 보안 · 개인정보

- **계정**: 1인 1계정(공용 계정 금지), 필요한 사람만 관리자, 퇴사 당일 삭제. 처음 받은 비밀번호는 첫 로그인 때 바꾸게 안내 띠가 뜨고, 바꾸지 않은 계정이 있으면 운영 점검이 막습니다. 비밀번호 10자 이상.
- **접근 통제**: SSH는 키로만, 22번 포트는 개발자 IP만. 관리 화면은 가능하면 병원 · 개발자 고정 IP만(`ADMIN_ALLOW_IPS`). 앱은 서버 안(127.0.0.1)에만 열고 바깥은 Caddy만.
- **접속기록**: 로그인 · 변경 · 예약/상담 목록 조회 · 내려받기를 계정 · 시각 · 접속지(IP)와 함께 남기고 지우지 않습니다(2년 이상). 매월 점검.
- **건강 정보**: 증상 메모 · 아픈 곳은 성함 · 연락처와 따로 동의를 받은 경우에만 저장(동의 시각 기록). 동의하지 않으면 빼고 예약할 수 있습니다. 보관 기간이 지나면 다른 정보와 함께 파기.
- **암호화**: 통신 HTTPS(HSTS), 비밀번호 scrypt, 백업 AES-256-GCM. 서버 디스크 암호화는 클라우드 옵션이 있으면 켭니다.
- **위탁 계약**: 클라우드 업체 · 문자 업체 · 운영 업체와 개인정보 처리 위탁 계약(목적 · 범위 · 재위탁 제한 · 안전성 확보 · 파기)을 맺고, 처리방침의 위탁 항목에 이름을 적습니다.
- **처리방침 갱신**: 위탁 업체 · 수집 항목 · 보관 기간 · 보호책임자가 바뀌면 고치고 시행일과 변경 이력을 남깁니다.
- **의료광고**: 치료 후기 · 전후 사진 · 최고 · 최저가 표현을 넣지 않습니다(`design/brand-book.md` 말투). 비급여 금액은 실제와 같게.
